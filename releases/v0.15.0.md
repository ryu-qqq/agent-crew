## 이 릴리스는

PR에 달린 GitHub 코드리뷰를 사람이 매번 직접 읽고 판단하는 수고를 덜기 위한 스킬을 추가합니다. `pr-review-triage`는 현재 브랜치(또는 지정한 PR)의 리뷰 코멘트를 gh CLI로 모아, 각 지적을 **실제 코드와 대조해 검증**한 뒤 수용/반론/보류로 분류하고 우선순위 잡힌 액션 플랜을 내놓습니다.

핵심은 단순 요약이 아니라 **판단**입니다. 리뷰어도 틀릴 수 있고 트레이드오프나 프로젝트 컨텍스트를 모를 수 있으므로, 받은 리뷰를 무비판적으로 수용하지 않고 "이 지적이 진짜 맞나"를 코드로 검증합니다. 스킬은 읽고 판단·제안까지만 하며, 실제 코드 수정·PR 답글·resolve는 사람이 승인한 뒤 별도로 합니다(HITL).

## 자산별 변경

### `skills/pr-review-triage/SKILL.md` — 신규

- **변경**: GitHub PR 리뷰 트리아지 진입점. 5단계 — 대상 PR 확정(현재 브랜치 자동 탐지 또는 PR 번호 인자) → 리뷰 수집(리뷰 본문·인라인 코멘트·대화 코멘트 3층위) → 코드와 대조한 판단 → ✅수용/🔁반론/⏸보류/☑️해결 분류 → 우선순위 액션 플랜 제시. 도구를 read-only(Bash·Read·Glob·Grep)로 제한해 "읽고 판단까지만"의 HITL 경계를 구조적으로 강제합니다.
- **개선**: 신규. 그동안 리뷰가 달릴 때마다 사람이 직접 읽고 항목별로 대응을 판단해야 했습니다 — 자산화로 그 판단의 1차 정리를 자동화하되, 적용은 사람 승인 뒤로 분리했습니다.
- **동기**: PR마다 반복되는 "리뷰 읽고 무엇부터 어떻게 대응할지 정하기"가 번거롭고, 리뷰를 맹목적으로 수용하면 잘못된 수정으로 이어진다는 문제에서 출발했습니다. 어느 프로젝트의 GitHub PR에서나 재발하는 패턴이라 공유 자산이 적합합니다.
- **설계 못박음**: ⓐ **프로젝트 비종속** — 절대경로·프로젝트명·특정 리뷰어 없이 `.claude/project.yaml`·gh 기본값으로 동작. ⓑ **맹목 수용 금지** — 각 지적을 해당 파일·라인을 직접 Read해 검증한 뒤 분류(소비 환경에 `superpowers:receiving-code-review`가 있으면 그 규율을 따르되 없어도 원칙 동일). ⓒ **HITL 경계** = 조회·판단·초안까지는 read-only로 직접, 코드 수정·PR 답글·resolve·push는 사람 승인 후 스킬 밖. ⓓ 불확실한 항목은 추측으로 수용/반론에 밀지 않고 불확실성을 드러내 사용자에게 판단을 넘깁니다.
